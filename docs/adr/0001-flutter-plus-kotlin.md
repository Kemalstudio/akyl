# 1. Flutter для логики, Kotlin для системных вызовов

**Дата:** 28.09.2026 · **Статус:** принято

## Контекст

ТЗ называет проект «нативным Android», но структура репозитория в том же ТЗ —
Flutter-приложение с Kotlin только для системных вызовов. Нужно было выбрать
одно.

## Решение

Flutter для всей логики, Kotlin — только для телефонии, SMS, контактов
и фонового микрофона.

## Почему

- Ядро (NLU, поиск контакта, диалог) становится чистым Dart и проверяется
  юнит-тестами за секунды, без эмулятора. Сценарии С1–С8 из ТЗ — это 15
  тестов, которые гоняются на каждый push.
- `sherpa_onnx` имеет официальный пакет для Flutter: главная зависимость
  этапа 2 доступна без написания своего моста.
- Бюджет задержек это не ломает: тяжёлые куски — STT и NLU — всё равно
  выполняются в нативном коде через ONNX Runtime, Dart только оркеструет.

## Чем платим

- Размер APK вырастает на несколько мегабайт рантайма Flutter при лимите
  в 150 МБ, где модели уже занимают около 200 МБ (см. docs/models.md).
- Каждое обращение к Android идёт через MethodChannel — десятки микросекунд,
  на фоне бюджета в 1000 мс несущественно.

## Альтернатива

Полностью нативный Kotlin. Отклонён: логика диалога тогда тестируется только
на устройстве или через Robolectric, а это медленнее на порядок и делает
разработку NLU на этапе 3 заметно дороже.
